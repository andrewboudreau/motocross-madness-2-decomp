## .text coverage

Rules (all in `tools/rebuild_coverage.py`):

- Registered extents are `target_va`/`target_size` from calibration cases and
  `*targets.json`. A `NEAR_MISS_INDEX` row without a registered size runs from
  its VA to the first alignment padding (bounded by the next registered
  start); its score denominator is not a retail size (e.g. `0x0050c960` scores
  227 compared bytes but is 3,742 bytes long, matching
  [UNATTRIBUTED](UNATTRIBUTED.md)).
- Padding: a 0xcc/0x90 run that starts on a decoded instruction boundary right
  after `ret`/`jmp`/`int3`/`nop` and ends on a 16-byte boundary, or that ends
  on a 16-byte boundary right after a dword jump-table entry pointing into the
  preceding 64 KiB. Immediate/displacement bytes are never padding.
- Unattributed bytes are split at padding into ranges; each is at least one
  function. Nearest source uses the `tools/nearest_source.py` ordering
  (absolute distance to a `__FILE__` xref; deltas are xref minus range start).

that library does not define `DirectInputCreateEx`, which retail imports from
DINPUT.dll; retail also imports `DirectDrawCreateEx`/`DirectDrawEnumerateA`
from `blade.dll` (there is no DDRAW.dll import). So the link used a DirectX
7-era `dinput.lib` and a `blade.dll` import library (strong inference);
neither is in the private bundle. The other thunk modules have SP3 import
libraries (`D3DRM`, `VFW32`, `IMM32`, `DSOUND`, `WSOCK32`, `DPLAYX`). The
thunk order (blade, d3drm, msvfw32, imm32, dsound, wsock32, dinput, dplayx,
then LIBCMT) is the order in which the linker resolved these libraries; it
constrains the rebuild's library order (strong inference).

The EH tail is emitted by the compiler with each function that has an unwind
map; it is rebuilt by compiling the owning game functions, not separately.

### Imports

There are 15 DLLs and 244 functions; 13 functions are imported by ordinal
(10 WSOCK32, 2 DSOUND, 1 DPLAYX).

**Descriptor order:** KERNEL32, USER32, GDI32, ADVAPI32, SHELL32, ole32,
**blade**, d3drm, WINMM, MSVFW32, IMM32, DSOUND, WSOCK32, DINPUT, DPLAYX.

**IAT order:** sorted by ASCII DLL name, from ADVAPI32 at 0x00550000 to ole32
at 0x005503fc.

Authentic LINK test links confirm two rules (confirmed):

- The descriptor order follows the order of import libraries on the command
  line. Libraries pulled in only through LIBCMT's `/DEFAULTLIB` come after.
- The IAT is always sorted by DLL name. Within one DLL, the function order is
  the order of first reference: objects in command-line order, then library
  members.

What this means for a rebuild:

- **Library list:** retail matches the VC6 AppWizard list
  `kernel32 user32 gdi32 [winspool comdlg32] advapi32 shell32 ole32 [oleaut32 uuid odbc32 odbccp32]`
  (bracketed libraries leave no trace), followed by
  `blade.lib d3drm.lib winmm.lib vfw32.lib imm32.lib dsound.lib wsock32.lib dinput.lib dplayx.lib`.
- **KERNEL32 order:** its 121 entries mix imports that only CRT code
  references (61 such slots) with imports that game code uses. Object order
  and per-object reference order therefore decide the bytes of the IAT, the
  ILT and the hint/name table.

**Hint check against the VC6 import libraries (confirmed).** The tool compares
each import's hint or ordinal with the short-import members of the VC6 import
libraries:

- **241 of 244 match.** Every hint or ordinal is equal for kernel32, user32,
  gdi32, advapi32, shell32, ole32, d3drm (hint 17), winmm, vfw32, imm32, dsound
  (1 = `DirectSoundCreate`, 2 = `DirectSoundEnumerateA`), wsock32 and dplayx
  (4 = `DirectPlayLobbyCreateA`). The wsock32 ordinals map to
  `WSAGetLastError closesocket send WSAStartup socket gethostbyname htons inet_addr connect ioctlsocket`.
- **3 imports are not in VC6:**
  - `DINPUT.dll!DirectInputCreateEx` (hint 1): the VC6 `dinput.lib` is
    DirectX 5 and lacks it.
  - `blade.dll!DirectDrawEnumerateA` (hint 3) and `blade.dll!DirectDrawCreateEx`
    (hint 2): no VC6 library names `blade.dll`.

  So a rebuild needs a DirectX 7 SDK `dinput.lib` and a `blade.lib` made from
  a `.def`, whose export order must give hints 2 and 3. The game loads

- **Headers:** the VC6 `INCLUDE` headers are DirectX 5. IID_IDirectDraw7,

How `src/` uses resources:

- `Main.cpp` loads the icon with `LoadImage(instance, IDI_APPLICATION, IMAGE_ICON, ...)`.
  That is exactly the numeric group id 32512, so the `.rc` must use
  `32512 ICON "..."`, not a named ID.

- 1 icon group (4 images, in the order above) under id 32512;
- 1 VERSIONINFO with the values above, plus a StringFileInfo block whose keys
  and values must be copied from the private image;
- language 1033.
